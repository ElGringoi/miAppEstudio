Los 5 hallazgos más importantes

  1. Seguridad: las reglas de Firestore no están en el repo, el repo es público y cualquier cuenta de Google puede iniciar sesión → P0 del roadmap.
  2. Confiabilidad: ningún onSnapshot tiene callback de error → si falla un permiso, la app queda en un spinner para siempre.
  3. Fecha UTC: desde las 21:00 de Argentina la app cree que es mañana (ADR-0007).
  4. Contraste: los 38 botones principales tienen 3,17:1 (blanco sobre azul); el mínimo es 4,5:1.
  5. Arquitectura: App.tsx es el 36 % del front (4744 líneas); bundle único de 468 KB gzip (ADR-0005).

Cómo mantener esto vivo

  • Si un cambio de código hace falsa una sección "Hoy", se actualiza en el mismo PR (Definition of Done del contrato).
  • Decisión nueva → ADR nuevo en 08-decisiones.
  • Mapa de código → regenerar archify.
  • Sitio HTML → npm run docs:site (no se edita a mano).

3. Reglas no negociables

Diseño

  1. Solo tokens semánticos. Nada de hex sueltos, nada de slate-* / blue-* en código nuevo. Si falta un color, se agrega a @theme y a fundamentos.md.
  2. Solo componentes del catálogo (ui/). Un botón nuevo es <Button variante=…>, no un <button className=…> a mano.
  3. Los 7 estados (cargando, vacío, error, offline, parcial, sin permiso, éxito) están definidos en la spec y en el código.
  4. Contraste medido, no estimado: texto ≥ 4,5:1, bordes de controles y foco ≥ 3:1.
  5. Áreas táctiles ≥ 44 px, foco visible, prefers-reduced-motion respetado.
  6. Copy en español rioplatense, con el glosario de ux-writing.md. Cero textos en inglés en la UI.
  7. Sin emojis como íconos estructurales (navegación, botones, estados).

Código

  1. TypeScript estricto, sin any. import type para tipos (CLAUDE.md).
  2. Lógica de negocio (XP, rachas, fechas) en funciones puras con test, no dentro de componentes.
  3. Fecha "hoy" siempre local de Argentina (cuando exista hoyLocal()), nunca toISOString().slice(0, 10).
  4. Cada onSnapshot con callback de error.
  5. Escrituras que tocan más de un doc (XP + entidad) en writeBatch / runTransaction.
  6. Borrar algo = limpiar sus referencias en el mismo batch.

Seguridad

  1. Ningún secreto con prefijo VITE_. Las keys de terceros viven solo en Vercel.
  2. Nada de .env en commits.
  3. Cambiar firestore.rules exige correr los tests del emulador.
  4. HTML generado desde contenido del usuario o de terceros: escapado antes de dangerouslySetInnerHTML.

Proceso

  1. PRs chicos: un objetivo por PR. Mover código y cambiar comportamiento van en PRs separados.
  2. Mensajes de commit en español informal ("Agrego X", "Corrijo Y"), sin prefijos (CLAUDE.md).
  3. Antes de abrir el PR: npm run lint, npx tsc -b, npm run build (y npm test cuando exista). Pegar el resultado en la descripción.
  4. Un PR que empeora un número de criterios-objetivos.md explica por qué en la descripción.
  5. Las decisiones que cambian arquitectura, esquema, estilo o dependencias grandes llevan ADR (sección 5).

Inbox de QUESTFLOW — cómo escribe un agente

El Inbox es una sección del Segundo Cerebro. Ahí aparece todo lo que entra sin clasificar, y el usuario después decide si cada cosa es una nota, una idea, una tarea, una misión, o algo de una persona o un grupo.

Un agente externo (el que trae mensajes recientes, o el que lee Gmail) entrega cosas al Inbox escribiendo documentos en Firestore. La app no tiene backend ni API: escuchar esa colección es todo lo que hace falta, y lo nuevo aparece en la app en tiempo real.

Dónde está la app

Producciónhttps://mi-app-estudio-gamma.vercel.app
Repohttps://github.com/ElGringoi/miAppEstudio
Base de datosCloud Firestore del proyecto Firebase de la app (el project id está en la variable VITE_FIREBASE_PROJECT_ID de Vercel)
Colecciónusuarios/{uid}/inbox

{uid} es el uid de Firebase Auth del usuario. Se ve en Firebase Console → Authentication → Users.

Cómo autenticarse

Con una service account del proyecto Firebase (Firebase Console → Project settings → Service accounts → Generate new private key) y el Admin SDK. El Admin SDK no pasa por las reglas de seguridad, así que no hace falta tocarlas.

La clave de la service account es una credencial con acceso total a la base. Va en los secrets del agente, nunca en un repo. Este repo es público.

Formato del documento

{
  texto:      string;   // obligatorio: el contenido
  origen:     'agente' | 'gmail';   // 'manual' lo usa solo la app
  recibidoEn: string;   // ISO 8601 con hora, ej. "2026-10-06T14:32:00-03:00"
  procesado:  false;

  // opcionales — omitirlos si no hay dato, NUNCA mandar null ni undefined
  titulo?:    string;   // ej. el asunto del mail
  remitente?: string;   // ej. "Martín (WhatsApp)" o "facturas@banco.com"
  url?:       string;   // link al original (el mail en Gmail, el mensaje, etc.)
}

La app ordena por recibidoEn, de más nuevo a más viejo. Los campos procesado, procesadoComo y procesadoEn los maneja la app: el agente solo crea documentos con procesado: false y no los modifica después.

Para no duplicar un mensaje que ya entregaste, usá un id de documento estable derivado del original (por ejemplo gmail-<messageId>) y escribí con set: si ya existe, se pisa con el mismo contenido en vez de crear otro.

Ejemplo (Node, Admin SDK)

import { initializeApp, cert } from 'firebase-admin/app';
import { getFirestore } from 'firebase-admin/firestore';

initializeApp({ credential: cert(JSON.parse(process.env.FIREBASE_SERVICE_ACCOUNT)) });
const db = getFirestore();

await db.doc(`usuarios/${process.env.QUESTFLOW_UID}/inbox/gmail-${mensaje.id}`).set({
  texto:      mensaje.cuerpo,
  titulo:     mensaje.asunto,
  remitente:  mensaje.de,
  url:        `https://mail.google.com/mail/u/0/#inbox/${mensaje.id}`,
  origen:     'gmail',
  recibidoEn: new Date(mensaje.fecha).toISOString(),
  procesado:  false,
});

Si cambia el tipo FSInboxItem en front/src/types.ts, hay que actualizar este archivo.

Visión del producto

El problema

Estudiar, entrenar, leer, ordenar la plata y cuidar los vínculos son cosas que se hacen todos los días y cuyo progreso no se ve. Las apps sueltas (un tracker de hábitos, un calendario, una de gastos, una de notas) reparten la información y ninguna premia el esfuerzo acumulado.

La propuesta

miAppEstudio convierte la vida diaria en un personaje de RPG que sube de nivel.

  • Cada hábito, capítulo leído, ejercicio o tarea de la facultad suma XP a un stat (Fuerza, Salud, Inteligencia, Agilidad, Carisma, Fe).
  • Los stats arman un nivel principal, un rango (E → D → C → B → A → S → SS → Monarch) y una clase (Guerrero, Mago, Paladín…).
  • Todo vive en una sola app: agenda, gimnasio, estudio, misiones, finanzas, un diario de noticias y un "Segundo Cerebro" para notas y personas.

Usuario

Hoy es una app de un solo usuario (Gastón): estudiante universitario en Argentina que entrena, lee y quiere ordenar su semana. Usa la app en el celular durante el día y en la compu para planificar.

Principios de producto

  1. Una acción, una recompensa visible. Todo lo que se completa muestra su XP en menos de 1 segundo.
  2. Lo de hoy primero. La pantalla de inicio responde "¿qué hago ahora?" sin scroll en el celular.
  3. Nada se pierde. Si falla la red, la app sigue andando con la caché local y lo dice.
  4. Terminar es parte del diseño. La Gaceta tiene última página; el día tiene cierre.
  5. Los datos son del usuario. Se pueden exportar completos y borrar (ver privacidad).

Estilo e identidad visual

Decisión (2026-10-19): dirección C · Gremio. Claymorphism + Vibrant & Block-based, adaptado a modo oscuro. Elegida por Gastón entre 3 direcciones generadas con UI/UX Pro Max. Registro: ADR-0004.

La idea en una frase

La app es la sala del gremio: un lugar cálido, de bloques gordos y táctiles, donde cada quest completada se siente como apretar un botón de verdad y ver subir la barra.

EsNo es
Cálido: marrones tostados, ámbar de racha, verde de progresoFrío: azul tecnológico, neón, glassmorphism
Táctil: botones con "escalón" que se hunden al tocarlosPlano: botones sin respuesta física

Por qué C

  1. El corazón de la app son las rachas y los hábitos, y el catálogo de UI/UX Pro Max recomienda para "Habit Tracker" exactamente este estilo: Claymorphism + Vibrant & Block-based, con paleta "ámbar de racha + verde de progreso".
  2. El feedback físico (botón que se hunde, barra que rebota) refuerza el loop "una acción, una recompensa visible" de la visión.
  3. Se lee bien de noche: fondo marrón muy oscuro en vez de negro azulado; contraste de texto 17,4:1.

Costo asumido: es la dirección de migración más alta (tokens, fuentes y forma de todas las cards). Se hace por etapas, ver roadmap fase P3.

Reglas de color

  1. Texto oscuro sobre color claro. Todo botón relleno usa su on-* oscuro. Nunca blanco sobre ámbar o verde (el error de hoy: blanco sobre #4d8eff = 3,17:1 en 38 botones).

  3. Nunca solo color: estado completado = check + color; error = ícono + texto.
  4. Prohibido el hex suelto en componentes: solo tokens (criterio C5).

Problemas del modelo

  1. Sin validación de esquema. Los docs se castean con as FSHabito (App.tsx:310); un campo mal escrito no se detecta.
  2. Referencias sin integridad. Borrar una misión no limpia los prerequisitos ni los linkedMisionIds que la apuntan.
  3. Arrays embebidos que crecen. setsLog, capitulos y materiales viven dentro del doc padre; Firestore corta en 1 MiB por documento.
  4. Colección muerta. objetivos_cha se lee y nunca se escribe.
  5. Fechas como string UTC (constants.tsx:6-7), ver ADR-0007.

Objetivo (to-be)

  • Esquema validado en un solo lugar. Cada colección tiene un conversor withConverter en data/ que valida al leer y al escribir.
  • Campo schemaVersion en cada doc nuevo, para migrar sin romper datos viejos.
  • Limpieza de referencias al borrar: misiones (prerequisitos, rocas), notas (links de personas y grupos). Va en el mismo writeBatch, como ya hace deleteGrupo (App.tsx:1744-1760).
  • Sacar objetivos_cha o darle una pantalla que lo escriba.
  • setsLog a subcolección si un ejercicio supera unas 200 series registradas.
  • Las reglas de Firestore validan los mismos tipos (ver firestore-rules.md).

Reglas de Firestore

Decisión: ADR-0006. Esta página es la propuesta; el archivo real firestore.rules se crea en la fase P0 del roadmap.

Hoy (as-is)

  • No hay firestore.rules en el repo ni en su historial de git. firebase.json solo tiene hosting (sin bloque firestore).
  • Las reglas que protegen la base viven solo en la consola de Firebase y nadie puede revisarlas desde el código.
  • La app lee y escribe todo desde el navegador (front/src/App.tsx), así que las reglas son la única defensa.
  • El agente Gmail usa el Admin SDK, que saltea las reglas (docs/INBOX_AGENTE.md).

Primer paso (15 min): Firebase Console → Firestore → Reglas → copiar el contenido a firestore.rules en la raíz y agregar a firebase.json:

{ "firestore": { "rules": "firestore.rules" } }

Si las reglas actuales son allow read, write: if request.auth != null o de "modo de prueba", cualquier cuenta de Google puede leer los datos de Gastón (personas con teléfono, finanzas, notas). Es el riesgo más alto del proyecto.

Objetivo (to-be): reglas propuestas

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // ── Helpers ────────────────────────────────────────────────
    function esDueno(uid) {
      return request.auth != null && request.auth.uid == uid;
    }
    function texto(v, max) { return v is string && v.size() > 0 && v.size() <= max; }
    function fecha(v) { return v is string && v.matches('^[0-9]{4}-[0-9]{2}-[0-9]{2}$'); }
    function statKey(v) {
      return v in ['fuerza', 'salud', 'inteligencia', 'agilidad', 'carisma', 'fe'];
    }

    match /usuarios/{uid} {

      // stats/main: solo los 6 stats, cada uno { xp: number }
      match /stats/{docId} {
        allow read: if esDueno(uid);
        allow write: if esDueno(uid) && docId == 'main'
          && request.resource.data.keys().hasOnly(
               ['fuerza', 'salud', 'inteligencia', 'agilidad', 'carisma', 'fe']);
      }

      match /habitos/{id} {
        allow read, delete: if esDueno(uid);
        allow create, update: if esDueno(uid)
          && texto(request.resource.data.nombre, 120)
          && statKey(request.resource.data.stat)
          && (!('completedDates' in request.resource.data)
              || request.resource.data.completedDates.size() <= 400);
      }

      match /transacciones/{id} {
        allow read, delete: if esDueno(uid);
        allow create, update: if esDueno(uid)
          && request.resource.data.monto is number
          && request.resource.data.monto > 0
          && request.resource.data.tipo in ['ingreso', 'gasto']
          && fecha(request.resource.data.fecha);
      }

      // El cliente solo crea capturas manuales; el agente usa Admin SDK
      match /inbox/{id} {
        allow read, delete: if esDueno(uid);
        allow create: if esDueno(uid) && request.resource.data.origen == 'manual';
        allow update: if esDueno(uid)
          && request.resource.data.diff(resource.data).affectedKeys()
               .hasOnly(['procesado', 'procesadoComo', 'procesadoEn']);
      }

      // Resto de colecciones conocidas: solo dueño, sin validación fina (todavía)
      match /{coleccion}/{id} {
        allow read, write: if esDueno(uid) && coleccion in [
          'eventos', 'tareas', 'misiones', 'rutinas', 'libros', 'materias',
          'diario', 'objetivos_cha', 'sueldos_meta', 'presupuestos',
          'metas_ahorro', 'personas', 'grupos', 'rocas',
          'diario_prefs', 'cerebro_prefs'
        ];
      }
    }

    // Todo lo demás, cerrado
    match /{document=**} {
      allow read, write: if false;
    }
  }
}

Por qué la lista de colecciones: en Firestore, si dos match aplican al mismo documento, alcanza con que uno permita. Si el comodín /{coleccion}/{id} incluyera habitos, saltearía la validación de arriba. Por eso el comodín nombra solo las colecciones sin reglas propias.

Opcional — cerrar el registro: si la app es solo para Gastón, agregar a esDueno la condición request.auth.uid in ['<uid de Gastón>']. El uid no es secreto (aparece en las rutas), así que puede estar en el repo.

Runbook: qué hacer cuando algo falla

Formato: síntoma → causa probable → cómo verificar → arreglo. Primero buscá el síntoma en la tabla de abajo y después andá a la sección.

SíntomaSección
La app queda en "Loading hero data…"Firestore permission-denied
El chat responde raro o "con tus datos" siempreGroq caído o sin key
La Gaceta muestra ensayos viejos o pocas notasLa Gaceta degradada o vacía
Desaparecieron los eventos de GoogleToken de Calendar vencido
Errores de "quota exceeded"Cuota de Firestore
El sitio no carga o da 404/500 tras un pushDeploy roto

Firestore permission-denied

  • Síntoma: spinner "Loading hero data…" para siempre después de iniciar sesión.
  • Causa probable: las reglas de Firestore rechazan alguna colección (por ejemplo, después de cambiar reglas en la consola). Como ningún onSnapshot tiene callback de error (App.tsx:304-339), la app nunca se entera.
  • Verificar: DevTools → Console: buscar FirebaseError: Missing or insufficient permissions. Firebase Console → Firestore → Reglas: ver la fecha del último cambio.
  • Arreglo: volver a la versión anterior de las reglas (la consola guarda historial) o aplicar la propuesta de firestore-rules.md. Solución de fondo: callback de error en cada listener (P1).

Groq caído o sin key

  • Síntoma: el chat siempre contesta con respuestas armadas desde las notas, sin redactar.
  • Causa probable: GROQ_API_KEY vencida o no configurada, cuota de Groq agotada, o Groq caído.
  • Verificar: DevTools → Network → cerebro-chat: el código (500 = falta key, 502 = error de Groq). Vercel → proyecto → Logs → filtrar por /api/cerebro-chat. Estado de Groq: groqstatus.com.
  • Arreglo: regenerar la key en Groq y actualizarla en Vercel → Environment Variables → Redeploy. Si es cuota, esperar el reset o cambiar GROQ_MODEL a uno más chico.

La Gaceta degradada o vacía

  • Síntoma: aviso "Sin conexión: edición de respaldo…" con red, o secciones con 0–1 notas.
  • Causa probable: más de la mitad de los feeds fallaron, o ESPN/Jolpica no respondieron (server/diario/edicion.ts:181-184). La función cachea la edición degradada solo 60 s y vuelve a intentar.
  • Verificar: abrir https://mi-app-estudio-gamma.vercel.app/api/edicion y mirar fuentesOk / fuentesTotal. Vercel Logs: buscar [diario] no se pudo parsear.
  • Arreglo: si un medio cambió la URL del feed, actualizarla en server/diario/fuentes.ts. Si falla todo, revisar que la función no pase los 30 s (vercel.json).

Token de Calendar vencido

  • Síntoma: los eventos de Google desaparecen del Calendario sin aviso.
  • Causa probable: el access token dura ~1 h (gcal_token_exp = ahora + 3500 s) y no hay refresh token. Un 401 lo borra en silencio (App.tsx:285-290). También se pierde al cerrar la pestaña (sessionStorage).
  • Verificar: DevTools → Application → Session Storage: si no hay gcal_token, está desconectado.
  • Arreglo: Ajustes → Conectar Google Calendar de nuevo. Solución de fondo: aviso "Se venció la conexión" + botón Reconectar (P2).

Cuota de Firestore

  • Síntoma: errores resource-exhausted o quota exceeded en la consola.
  • Causa probable: plan Spark (gratis): 50 000 lecturas y 20 000 escrituras por día. Con 20 listeners abiertos, cada apertura de la app lee todas las colecciones completas.
  • Verificar: Firebase Console → Firestore → Uso.
  • Arreglo inmediato: esperar al reset diario (medianoche hora del Pacífico). De fondo: listeners por pantalla (rendimiento-confiabilidad.md).

Deploy roto en Vercel

  • Síntoma: la URL de producción da error o muestra una versión vieja.
  • Causa probable: falló tsc -b o vite build en Vercel (por ejemplo, una dependencia no declarada o un error de tipos).
  • Verificar: Vercel → Deployments → el último → Build Logs. Localmente: npm ci y después npm run build.
  • Arreglo: Vercel → Deployments → el último que funcionó → Promote to Production (rollback inmediato). Después arreglar el build en una rama.

  • Estado: 📝 propuesta
  • Fecha: 2026-10-19
  • Decide: Gastón
  • Relacionado: estados-y-excepciones.md casos 1 y 2, rendimiento-confiabilidad.md

Contexto

front/src/utils/constants.tsx:6-7:

export const HOY = new Date().toISOString().slice(0, 10);
export const getToday = () => new Date().toISOString().slice(0, 10);

toISOString() es UTC. Argentina es UTC−3, así que desde las 21:00 la app cree que ya es mañana:

  • La reflexión del Cierre del día (que se abre justo después de las 21:00) se guarda con la fecha de mañana (App.tsx:1483).
  • Además, HOY se calcula una sola vez al cargar el módulo: si la app queda abierta pasada la medianoche, sigue en el día anterior.

La Gaceta ya resuelve esto bien con hoyArgentina() en server/diario/fecha.ts.

OpciónA favorEn contra
